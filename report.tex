\section{Introduction to MLOps}\label{sec:intro}

\subsection{D1.1: Introduction to MLOps}
Machine Learning Operations (MLOps) is a set of best practices that combines Machine Learning (ML), DevOps, and Data Engineering to manage the full lifecycle of ML models in production. While traditional software development has evolved from waterfall to agile to DevOps methodologies, ML applications present unique challenges that require a new approach.

The fundamental difference between traditional software and ML systems is that ML is not just code—it is \textbf{code plus data}. This relationship means that both code and data must evolve together in a controlled manner. Without a systematic MLOps approach, divergence between code and data evolution can cause problems in production, hinder smooth deployment, and lead to results that are hard to trace or reproduce.

\textbf{Key differences from traditional development paradigms:}
\begin{itemize}
    \item \textbf{Waterfall}: Linear, non-iterative development unsuitable for dynamic ML projects where requirements change based on model performance and data drift.
    \item \textbf{Agile}: Iterative but doesn't address the data-centric nature of ML systems or the need for continuous model monitoring.
    \item \textbf{DevOps}: Focuses on code CI/CD but lacks mechanisms for data versioning, model registry, and ML-specific monitoring.
    \item \textbf{MLOps}: Extends DevOps with three interconnected cycles—data, model, and code—ensuring reproducibility, traceability, and continuous improvement.
\end{itemize}

The MLOps workflow consists of three main phases: \textbf{Build} (data ingestion, model training, testing, packaging, registering), \textbf{Deploy} (application testing, production release via CI/CD), and \textbf{Monitor} (monitoring data integrity, model drift, and application performance). These are enabled by key drivers: data, code, artifacts, middleware, and infrastructure.

\section{Continuous ML}\label{sec:continuous-ml}

This module covers Continuous Integration and Continuous Delivery (CI/CD) applied to machine learning pipelines. The core idea is borrowed from DevOps: every commit to the repository should trigger an automated pipeline that builds, tests, trains, evaluates, and potentially deploys a new model version---without manual intervention.

\subsection{D2.1: Continuous ML Pipeline Overview}

The implemented CI/CD pipeline for our Cats vs Dogs project is orchestrated using Jenkins, running on the AAU MLOps cluster (\texttt{daki-storage}, \texttt{172.24.198.42:8080}). The pipeline is defined in a \texttt{Jenkinsfile} and triggered automatically when Jenkins detects new commits in the repository.

\textbf{Pipeline stages (as defined in Jenkinsfile):}
\begin{enumerate}
    \item \textbf{Lint}: Flake8 checks the \texttt{src/} directory for PEP8 compliance (\texttt{max-line-length=100}). If the code does not pass linting, the pipeline stops immediately (fail-fast principle).
    \item \textbf{Test}: \texttt{pytest} runs all unit tests in \texttt{tests/} with coverage reporting (\texttt{--cov=src}). Test results are published as JUnit XML for Jenkins to display.
    \item \textbf{Build \& Push Docker}: A Docker image is built from \texttt{Dockerfile} (based on \texttt{python:3.11-slim}) and tagged with both the Git commit hash (\texttt{\$\{GIT\_COMMIT\}}) and \texttt{latest}. Both tags are pushed to the local Docker Registry at \texttt{172.24.198.42:5000}.
    \item \textbf{Fetch Data}: DVC pulls the versioned dataset from the MinIO S3 storage (\texttt{s3://daki4-26-gr3/dvc} on \texttt{172.24.198.42:9000}), ensuring the training always uses data consistent with the current code version.
    \item \textbf{Train}: The model is trained via \texttt{python src/train.py --config configs/config.yaml} with MLflow tracking enabled. All hyperparameters and per-epoch metrics are logged to the MLflow server.
    \item \textbf{Evaluate}: The trained model is evaluated on the test set via \texttt{python src/evaluate.py}, computing accuracy, precision, recall, and F1-score.
    \item \textbf{Register Model}: On the \texttt{main} branch only, the pipeline queries the latest MLflow run. If accuracy $\geq$ 80\%, the model is registered in the MLflow Model Registry under the name \texttt{cats-vs-dogs-model}. If accuracy is below the threshold, the pipeline fails.
\end{enumerate}

In addition to the Jenkins pipeline, a \textbf{GitHub Actions CI workflow} (\texttt{.github/workflows/ci.yml}) runs on every push and pull request to \texttt{main} and \texttt{develop}. This workflow installs dependencies, runs all pre-commit hooks (\texttt{pre-commit run --all-files}), and executes the test suite. This provides a cloud-based safety net that complements the local Jenkins pipeline.

\textbf{Local pre-commit hooks} (\texttt{.pre-commit-config.yaml}) also run before each commit on the developer's machine. These include: trailing whitespace removal, YAML validation, large file detection ($>$5\,MB), private key detection, merge conflict checks, secret scanning via \texttt{detect-secrets}, and Flake8 linting.

\textbf{Branching strategy:} We use a three-branch model: \texttt{main} is the protected production branch, \texttt{development} is the persistent integration branch for new features, and temporary feature branches (e.g., \texttt{Peter}, \texttt{test-required-check}) are created for isolated work. Feature branches are merged into \texttt{development} and then into \texttt{main} after passing all pipeline stages. Branch protection is enabled on \texttt{main}, requiring a successful CI check (GitHub Actions) before merges are allowed. The Jenkins pipeline runs on all branches, but model registration only occurs on \texttt{main}.

\textbf{Lineage and tracking:} The pipeline provides traceability through three systems working together:
\begin{itemize}
    \item \textbf{Git}: Versions all code. The commit hash is used as the Docker image tag, linking every container to its exact source code.
    \item \textbf{DVC}: Versions the dataset via MinIO. Each \texttt{.dvc} file in Git links a code version to a specific data version.
    \item \textbf{MLflow}: Tracks all experiment runs including hyperparameters (model name, learning rate, batch size, epochs, optimizer, seed), per-epoch metrics (train/val loss and accuracy), final best validation accuracy, and the model artifact (\texttt{best\_model.pt}).
\end{itemize}

Together, these ensure that any registered model can be traced back to the exact code, data, and configuration that produced it.

\section{Scalable Training}\label{sec:scalable-training}

This module addresses techniques for scaling deep learning training across multiple GPUs and nodes. As model sizes and dataset volumes grow, training on a single GPU becomes infeasible---both in terms of memory and time. Scalable training techniques enable time compression (faster convergence) and the ability to train larger models.

\subsection{D3.1: Speedup Estimate from Parallelization}

To estimate the theoretical speedup of our ResNet18 training through parallelization, we apply Gustafson's Law, which is better suited for deep learning workloads than Amdahl's Law because we typically scale the problem size (batch size) as we add GPUs:

\begin{equation}
    S(P) = P - a \cdot (P - 1)
    \label{eq:gustafson}
\end{equation}

where $P$ is the number of GPUs and $a$ is the sequential fraction of the workload. For multi-GPU training on a single node, a typical sequential fraction is approximately $a = 0.15$ (accounting for gradient synchronization, data loading overhead, and control flow).

\textbf{Estimated speedups} using the AAU cluster RTX Pro 4000 Ada GPUs:

\begin{table}[h]
\centering
\caption{Estimated training speedup using Gustafson's Law ($a = 0.15$).}
\label{tab:gustafson}
\begin{tabular}{@{} c c c @{}}
\toprule
\textbf{GPUs ($P$)} & \textbf{Speedup $S(P)$} & \textbf{Efficiency} \\
\midrule
1 & 1.00$\times$ & 100\% \\
2 & 1.85$\times$ & 92.5\% \\
3 & 2.70$\times$ & 90.0\% \\
\bottomrule
\end{tabular}
\end{table}

With 3 GPUs (the number of GPU worker nodes available on the AAU cluster), Gustafson's Law predicts a speedup of approximately $2.70\times$ with 90\% parallel efficiency. In practice, the actual speedup is often slightly lower due to communication overhead in gradient synchronization (All-Reduce) and potential data loading bottlenecks.

\subsection{D3.2: Scaling Estimate to Halve Test Loss}

Using the scaling laws established by Kaplan et al. \cite{kaplan2020scaling}, test loss follows an inverse power law as a function of compute $C$, dataset size $D$, and model parameters $N$:

\begin{equation}
    L(x) = \left(\frac{x_0}{x}\right)^{\alpha}
    \label{eq:powerlaw}
\end{equation}

To halve the test loss ($L_{\text{new}} = 0.5 \cdot L_{\text{current}}$), we need:
\begin{equation}
    \frac{x_{\text{new}}}{x_{\text{current}}} = 2^{1/\alpha}
\end{equation}

Using the constants found for LLMs (as suggested in the exercise), with $\alpha_C \approx 0.050$ for compute, $\alpha_D \approx 0.095$ for dataset size, and $\alpha_N \approx 0.076$ for parameters:

\begin{table}[h]
\centering
\caption{Estimated scaling factors required to halve test loss.}
\label{tab:scaling}
\begin{tabular}{@{} l c c @{}}
\toprule
\textbf{Scaling Dimension} & \textbf{$\alpha$} & \textbf{Factor $2^{1/\alpha}$} \\
\midrule
Compute & 0.050 & $\sim 1.1 \times 10^{6}$ \\
Dataset size & 0.095 & $\sim 1{,}500\times$ \\
Parameters & 0.076 & $\sim 9{,}000\times$ \\
\bottomrule
\end{tabular}
\end{table}

These numbers illustrate the diminishing returns of scaling: halving the test loss requires enormous increases in resources. For our ResNet18 model with approximately 11 million parameters, this would mean scaling to $\sim$99 billion parameters, or increasing the dataset from $\sim$25{,}000 images to $\sim$37.5 million images, or increasing compute by a factor of over one million. This highlights why the power law represents diminishing returns when viewed on a linear scale, even though it appears linear in log-log space.

\subsection{D3.3: Multi-GPU Parallelization (DDP)}

We implemented data parallelism using PyTorch's Distributed Data Parallel (DDP) in a dedicated training script (\texttt{train\_ddp.py}). DDP replicates the model on each GPU, distributes micro-batches across GPUs, and synchronizes gradients via the NCCL All-Reduce operation after each backward pass.

\textbf{Implementation details:}
\begin{itemize}
    \item Backend: NCCL (optimized for NVIDIA GPUs)
    \item Launch: \texttt{torchrun --nproc\_per\_node=N train\_ddp.py}
    \item Each GPU processes a micro-batch; effective batch size = micro-batch $\times$ N GPUs
    \item \texttt{DistributedSampler} ensures no data overlap between GPUs
    \item Learning rate scaled linearly with the number of GPUs
\end{itemize}

\subsection{D3.5: Memory Optimization with AMP}

Automatic Mixed Precision (AMP) was implemented using PyTorch's \texttt{torch.cuda.amp} module. AMP automatically selects FP16 for operations that benefit from lower precision (convolutions, matrix multiplications) while keeping FP32 for numerically sensitive operations (loss computation, batch normalization).

\textbf{Implementation:}
\begin{verbatim}
scaler = torch.cuda.amp.GradScaler()
with torch.cuda.amp.autocast():
    output = model(input)
    loss = loss_fn(output, target)
scaler.scale(loss).backward()
scaler.step(optimizer)
scaler.update()
\end{verbatim}

\textbf{Expected benefits:}
\begin{itemize}
    \item \textbf{Memory savings}: $\sim$25--40\% VRAM reduction, allowing larger batch sizes
    \item \textbf{Speed}: Up to $2\times$ faster training on GPUs with Tensor Core support (RTX Pro 4000 Ada supports this)
    \item \textbf{Accuracy}: No significant accuracy degradation due to loss scaling preventing gradient underflow
\end{itemize}

\section{Scalable Inference}\label{sec:scalable-inference}

This module covers techniques for optimizing model inference: reducing model size, improving throughput, and maintaining accuracy. The goal is to maximize throughput while staying within specific latency and compute budgets.

\subsection{D4.1: Model Compression via Quantization}

Post-training quantization (PTQ) was applied to the ResNet18 model using PyTorch's FX graph mode static quantization. Static PTQ quantizes both weights \textit{and} activations to INT8, unlike dynamic quantization which only quantizes weights. A calibration dataset (320 synthetic images) was used to determine optimal quantization parameters (scale and zero-point) for each layer.

The 74.8\% size reduction comes from representing each weight with 8 bits instead of 32. The significant CPU speedup (up to 11.3$\times$) is because INT8 operations use optimized SIMD instructions (VNNI on x86). GPU inference was not benchmarked for INT8, as PyTorch static quantization targets CPU deployment. For GPU quantization, TensorRT or CUDA-native INT8 would be used.

The prediction agreement between FP32 and INT8 models confirms that ResNet architectures are stable under PTQ, consistent with findings reported by NVIDIA showing ResNet within 1\% accuracy of FP32 after quantization.

\textbf{Key findings:}
\begin{itemize}
    \item \textbf{Throughput saturates at batch size 16} ($\sim$170.8 img/s), after which throughput \textit{decreases} due to memory pressure exceeding CPU cache capacity.
    \item \textbf{Latency-throughput tradeoff}: Batch size 1 gives lowest latency (16.4 ms) but lowest throughput (61.1 img/s). Batch size 16 gives 2.8$\times$ higher throughput at the cost of higher total latency (93.7 ms per batch).
    \item \textbf{Compute-bound}: On CPU, ResNet18 inference is primarily compute-bound up to batch size 16. Beyond that, the workload becomes memory bandwidth-bound as data no longer fits in L3 cache, causing a dramatic throughput drop at batch size 64.
\end{itemize}

For a production deployment, batch size 8--16 would balance latency ($<$100 ms per batch) with near-peak throughput. Dynamic batching (as offered by e.g. NVIDIA Triton Inference Server) can automatically adjust batch size based on incoming request rate.

Global unstructured L1-norm pruning was applied at increasing sparsity levels to a pretrained ResNet18 (ImageNet, 1000 classes). Prediction agreement with the unpruned model was measured on 200 test samples:

\begin{table}[h]
\centering
\caption{Effect of pruning on prediction agreement.}
\label{tab:pruning}
\begin{tabular}{@{} r r r @{}}
\toprule
\textbf{Pruning (\%)} & \textbf{Agreement (\%)} & \textbf{Drop (pp)} \\
\midrule
0 & 100.0 & 0.0 \\
10 & 100.0 & 0.0 \\
20 & 99.0 & 1.0 \\

The results reveal a sharp ``accuracy cliff'' at approximately 50\% sparsity: the model maintains $>$97\% agreement up to 40\% pruning, but collapses catastrophically beyond 50\%. This cliff behavior is characteristic of unstructured magnitude pruning applied in a single shot. Iterative pruning with retraining between steps typically produces a more gradual degradation curve, allowing higher sparsity levels.

Note that unstructured pruning saves parameters but does not always translate to real inference speedup unless the hardware supports sparse operations. Structured pruning (removing entire filters/channels) yields actual speedups on standard hardware.

Even at 90\% sparsity (only 10\% of original weights non-zero), the pruned model recovers to 99.5\% prediction agreement with the unpruned model after 10 epochs of knowledge distillation. \subsection{D5.2: Endpoint Testing and Safeguarding}

For our Cats vs Dogs classification model deployed as an API endpoint, the following testing dimensions are relevant:

\textbf{Functional testing:}
\begin{itemize}
    \item Verify \texttt{POST /predict} returns correct JSON response with class label and confidence score.
    \item Test with valid cat and dog images to confirm correct classification.
    \item Test with proper error handling for missing or malformed request bodies.
\end{itemize}
This can be automated using \texttt{pytest} with the \texttt{requests} library, or via Postman/Newman for manual and CI/CD-integrated testing.

\textbf{Robustness testing:}
\begin{itemize}
    \item Submit non-image files (PDF, text) and verify graceful error responses.
    \item Submit corrupted image data and verify no server crash.
    \item Submit extremely large images to test memory limits.
    \item Submit images of objects that are neither cats nor dogs (out-of-distribution) to verify the model handles edge cases.
\end{itemize}

\textbf{Performance testing:}
\begin{itemize}
    \item Use Locust to simulate concurrent users and measure response times under load.
    \item Verify latency stays below acceptable thresholds (e.g., $<$200 ms for real-time classification).
    \item Identify the breaking point where throughput degrades.
\end{itemize}

\textbf{Security testing:}
\begin{itemize}
    \item Rate limiting to prevent abuse (e.g., max 100 requests/minute per client).
    \item Input validation to reject payloads exceeding maximum size.
    \item Authentication and API key management.
    \item OWASP ZAP for automated penetration testing (SQL injection, XSS).
\end{itemize}

\textbf{Safeguards against undesired input/output:}
For an image classification model, the primary safeguards are: (1) input validation---rejecting non-image files, oversized images, and rate limiting, (2) confidence thresholds---returning ``unknown'' when the model's softmax probability is below a threshold (e.g., 70\%), which guards against out-of-distribution inputs, and (3) output sanitization---ensuring the API never exposes internal model details or stack traces.

In our specific case, the most important safeguards are confidence thresholds (to handle images that are neither cats nor dogs) and rate limiting (to prevent resource exhaustion on edge devices with limited compute).
