\section{Introduction to MLOps}\label{sec:intro}

\subsection{D1.1: Introduction to MLOps}
Machine Learning Operations (MLOps) combines Machine Learning, DevOps, and Data Engineering to manage the full lifecycle of ML models in production. ML applications have unique challenges that traditional software does not have, because code alone is not enough. This requires a different approach than the waterfall, agile, and DevOps methodologies used in traditional software development.

ML systems differ from traditional software in one key way: ML is not just code, it is \textbf{code plus data}. Code and data must evolve together. If they drift apart, the model will fail in production and the results will be hard to trace or reproduce. For the Cats vs Dogs pipeline, this means every change to image preprocessing, augmentation, or the dataset must be versioned with code changes. Only then can any trained model be traced back to the exact data and code that produced it.

\textbf{Key differences from traditional development paradigms:}
\begin{itemize}
    \item \textbf{Waterfall}: Linear, non-iterative development unsuitable for dynamic ML projects where requirements change based on model performance and data drift.
    \item \textbf{Agile}: Iterative but does not address the data-centric nature of ML systems or the need for continuous model monitoring.
    \item \textbf{DevOps}: Focuses on code CI/CD but lacks mechanisms for data versioning, model registry, and ML-specific monitoring.
    \item \textbf{MLOps}: Extends DevOps with three linked cycles covering data, model, and code, to ensure reproducibility, traceability, and continuous improvement.
\end{itemize}

The MLOps workflow has three phases. \textbf{Build} includes data ingestion, model training, testing, packaging, and registration. \textbf{Deploy} includes application testing and production release via CI/CD. \textbf{Monitor} includes checking data integrity, detecting model drift, and tracking application performance. These three phases are enabled by data, code, artifacts, middleware, and infrastructure.

\section{Continuous ML}\label{sec:continuous-ml}

This module covers Continuous Integration and Continuous Delivery (CI/CD) applied to machine learning pipelines. The core idea comes from DevOps. Every commit to the repository triggers an automated pipeline that builds, tests, trains, evaluates, and potentially deploys a new model version without manual intervention.

\subsection{D2.1: Continuous ML Pipeline Overview}

The implemented CI/CD pipeline for our Cats vs Dogs project is run using Jenkins, running on the AAU MLOps cluster (\texttt{daki-storage}, \texttt{172.24.198.42:8080}). The pipeline is defined in a \texttt{Jenkinsfile} and triggered automatically when Jenkins detects new commits in the repository.

\textbf{Pipeline stages (as defined in Jenkinsfile):}
\begin{enumerate}
    \item \textbf{Lint}: Flake8 checks the \texttt{src/} directory for PEP8 compliance (\texttt{max-line-length=100}). If the code does not pass linting, the pipeline stops immediately (fail-fast principle).
    \item \textbf{Test}: \texttt{pytest} runs all unit tests in \texttt{tests/} with coverage reporting (\texttt{--cov=src}). Test results are published as JUnit XML for Jenkins to display.
    \item \textbf{Build \& Push Docker}: A Docker image is built from \texttt{Dockerfile.serve} (based on \texttt{pytorch/pytorch:2.0.0-cuda11.7-cudnn8-runtime}) and tagged with both the Git commit hash (\texttt{\$\{GIT\_COMMIT\}}) and \texttt{latest}. Both tags are pushed to the local Docker Registry at \texttt{172.24.198.42:5000}.
    \item \textbf{Fetch Data}: DVC pulls the versioned dataset from the MinIO S3 storage (\texttt{s3://pkj-catdog/dvc} on \texttt{172.24.198.42:9000}), ensuring the training always uses data consistent with the current code version.
    \item \textbf{Train}: The model is trained via \texttt{python src/train.py --config configs/config.yaml} with MLflow tracking enabled. All hyperparameters and per-epoch metrics are logged to the MLflow server.
    \item \textbf{Evaluate}: The trained model is evaluated on the test set via \texttt{python src/evaluate.py}, computing accuracy, precision, recall, and F1-score.
    \item \textbf{Quantize}: Post-training quantization is applied to the trained model via \texttt{python src/quantize\_benchmark.py}, producing a compressed INT8 model for CPU deployment.
    \item \textbf{Register Model}: On the \texttt{main} branch only, the pipeline queries the latest MLflow run. If accuracy $\geq$ 80\%, the model is registered in the MLflow Model Registry under the name \texttt{cats-vs-dogs-model}. If accuracy is below the threshold, the pipeline fails.
    \item \textbf{Deploy Model}: The latest registered model version is transitioned to Production stage in the MLflow Model Registry. Deployment metadata is logged as tags on the model version for tracking.
    \item \textbf{Deploy API}: The Docker image with the serving API is deployed, making the model available via the Flask REST endpoint at \texttt{172.24.198.42:5001}.
\end{enumerate}

In addition to the Jenkins pipeline, a \textbf{GitHub Actions CI workflow} (\texttt{.github/workflows/ci.yml}) runs on every push and pull request to \texttt{main} and \texttt{develop}. This workflow installs dependencies, runs all pre-commit hooks (\texttt{pre-commit run --all-files}), and executes the test suite. This provides a cloud-based safety net that backs up the local Jenkins pipeline.

\textbf{Local pre-commit hooks} (\texttt{.pre-commit-config.yaml}) also run before each commit on the developer's machine. These include trailing whitespace removal, YAML validation, large file detection ($>$5\,MB), private key detection, merge conflict checks, secret scanning via \texttt{detect-secrets}, and Flake8 linting.

\textbf{Branching strategy:} We use a three-branch model where \texttt{main} is the protected production branch, \texttt{development} is the persistent integration branch for new features, and temporary feature branches (e.g., \texttt{Peter}, \texttt{test-required-check}) are created for isolated work. Feature branches are merged into \texttt{development} and then into \texttt{main} after passing all pipeline stages. Branch protection is enabled on \texttt{main}, requiring a successful CI check (GitHub Actions) before merges are allowed. The Jenkins pipeline runs on all branches, but model registration only occurs on \texttt{main}.

\textbf{Lineage and tracking:} The pipeline provides traceability through three systems working together:
\begin{itemize}
    \item \textbf{Git}: Versions all code. The commit hash is used as the Docker image tag, linking every container to its exact source code.
    \item \textbf{DVC}: Versions the dataset via MinIO. Each \texttt{.dvc} file in Git links a code version to a specific data version.
    \item \textbf{MLflow}: Tracks all experiment runs including hyperparameters (model name, learning rate, batch size, epochs, optimizer, seed), per-epoch metrics (train/val loss and accuracy), final best validation accuracy, and the model artifact (\texttt{best\_model.pt}).
\end{itemize}

These three systems work together. Any registered model can be traced back to the exact code, data, and configuration that produced it. This enables debugging and reproducibility if the model drifts or fails in production (Sections \ref{sec:monitoring} and \ref{sec:post-deployment}). \section{Scalable Training}\label{sec:scalable-training}

This module addresses techniques for scaling deep learning training across multiple GPUs and nodes. As model sizes and dataset volumes grow, training on a single GPU cannot work well, both because of memory limits and time constraints. Scalable training techniques allow us to train models faster (quicker convergence) and to train larger models. For our Cats vs Dogs ResNet18 pipeline, faster training means we can iterate on hyperparameters more quickly and respond faster to model drift detected in the CI/CD pipeline (Section~\ref{sec:continuous-ml}).

\subsection{D3.1: Speedup Estimate from Parallelization}

To estimate the theoretical speedup of our ResNet18 training through parallelization, we apply Gustafson's Law. This law is better suited for deep learning workloads than Amdahl's Law because we typically scale the problem size (batch size) as we add GPUs. The formula is:

\begin{equation}
    S(P) = P - a \cdot (P - 1)
    \label{eq:gustafson}
\end{equation}

where $P$ is the number of GPUs and $a$ is the sequential fraction of the workload. For multi-GPU training on a single node, a typical sequential fraction is approximately $a = 0.15$ (accounting for gradient synchronization, data loading overhead, and control flow).

\textbf{Estimated speedups} using the AAU cluster RTX Pro 4000 Ada GPUs:

\begin{table}[h]
\centering
\caption{Estimated training speedup using Gustafson's Law ($a = 0.15$).}
\label{tab:gustafson}
\begin{tabular}{@{} c c c @{}}
\toprule
\textbf{GPUs ($P$)} & \textbf{Speedup $S(P)$} & \textbf{Efficiency} \\
\midrule
1 & 1.00$\times$ & 100\% \\
2 & 1.85$\times$ & 92.5\% \\
3 & 2.70$\times$ & 90.0\% \\
\bottomrule
\end{tabular}
\end{table}

With 3 GPUs (the number of GPU worker nodes available on the AAU cluster), Gustafson's Law predicts a speedup of approximately $2.70\times$ with 90\% parallel efficiency. In practice, the actual speedup is often slightly lower due to communication overhead in gradient synchronization (All-Reduce) and potential data loading bottlenecks.

\subsection{D3.2: Scaling Estimate to Halve Test Loss}

Using the scaling laws established by Kaplan et al. \cite{kaplan2020scaling}, test loss follows an inverse power law as a function of compute $C$, dataset size $D$, and model parameters $N$:

\begin{equation}
    L(x) = \left(\frac{x_0}{x}\right)^{\alpha}
    \label{eq:powerlaw}
\end{equation}

To halve the test loss ($L_{\text{new}} = 0.5 \cdot L_{\text{current}}$), we need:
\begin{equation}
    \frac{x_{\text{new}}}{x_{\text{current}}} = 2^{1/\alpha}
\end{equation}

Using the constants found for LLMs (as suggested in the exercise), with $\alpha_C \approx 0.050$ for compute, $\alpha_D \approx 0.095$ for dataset size, and $\alpha_N \approx 0.076$ for parameters:

\begin{table}[h]
\centering
\caption{Estimated scaling factors required to halve test loss.}
\label{tab:scaling}
\begin{tabular}{@{} l c c @{}}
\toprule
\textbf{Scaling Dimension} & \textbf{$\alpha$} & \textbf{Factor $2^{1/\alpha}$} \\
\midrule
Compute & 0.050 & $\sim 1.1 \times 10^{6}$ \\
Dataset size & 0.095 & $\sim 1{,}500\times$ \\
Parameters & 0.076 & $\sim 9{,}000\times$ \\
\bottomrule
\end{tabular}
\end{table}

These numbers show that we get less benefit from scaling each time we try it, since halving the test loss requires enormous increases in resources. For our ResNet18 model with approximately 11 million parameters, this would mean scaling to $\sim$99 billion parameters, or increasing the dataset from $\sim$25{,}000 images to $\sim$37.5 million images, or increasing compute by a factor of $\sim 1.1 \times 10^{6}$. On a linear scale, the power law shows we get less benefit each time, though it appears linear in log-log space.

\subsection{D3.3: Multi-GPU Parallelization (DDP)}

We implemented data parallelism using PyTorch's Distributed Data Parallel (DDP) in a dedicated training script (\texttt{train\_ddp.py}). DDP replicates the model on each GPU, distributes micro-batches across GPUs, and synchronizes gradients via the NCCL All-Reduce operation after each backward pass.

\textbf{Implementation details:}
\begin{itemize}
    \item Backend: NCCL (optimized for NVIDIA GPUs)
    \item Launch: \texttt{torchrun --nproc\_per\_node=N train\_ddp.py}
    \item Each GPU processes a micro-batch, and the effective batch size = micro-batch $\times$ N GPUs
    \item \texttt{DistributedSampler} ensures no data overlap between GPUs
\end{itemize}

Benchmark results were collected on the AAU AI-Lab's NVIDIA L4 GPUs with a batch size of 32 and 3 training epochs. Table~\ref{tab:ddp} compares single-GPU and two-GPU training time, memory usage, and validation accuracy.

\subsection{D3.4: Multi-Node Parallelization}

For multi-node training, the DDP setup was extended to run across multiple machines on the AAU cluster using \texttt{torchrun}:

\begin{verbatim}

  --rdzv_backend=c10d \
  --rdzv_endpoint=<master_ip>:29500 \

Multi-node training adds communication overhead because gradients must cross the network (Ethernet) instead of using fast GPU-to-GPU links (PCIe/NVLink). The AAU cluster nodes are connected via standard Ethernet, which limits the achievable speedup for communication-intensive workloads. Multi-node DDP was not benchmarked due to network access constraints between cluster nodes, but the implementation is in place via \texttt{scripts/launch\_multinode.sh}.

\subsection{D3.5: Memory Optimization with AMP}

Automatic Mixed Precision (AMP) was implemented using PyTorch's \texttt{torch.amp} module. AMP automatically selects FP16 for operations that benefit from lower precision (convolutions, matrix multiplications) while keeping FP32 for numerically sensitive operations (loss computation, batch normalization).

\textbf{Implementation:}
\begin{verbatim}
from torch.amp import GradScaler, autocast
scaler = GradScaler("cuda")
with autocast("cuda"):
    output = model(input)
    loss = loss_fn(output, target)
scaler.scale(loss).backward()
scaler.step(optimizer)
scaler.update()
\end{verbatim}

\section{Scalable Inference}\label{sec:scalable-inference}

This module covers how to optimize model inference by reducing model size, improving throughput, and keeping accuracy high. The goal is to maximize throughput while staying within specific latency and compute budgets.

\subsection{D4.1: Model Compression via Quantization}

Post-training quantization (PTQ) was applied to the ResNet18 model using PyTorch's FX graph mode static quantization. Static PTQ quantizes both weights and activations to INT8. Dynamic quantization only quantizes weights. A calibration dataset (320 synthetic images) was used to determine the best quantization parameters (scale and zero-point) for each layer.

\subsection{D5.2: Endpoint Testing and Safeguarding}

Deployment via APIs needs hardening against malicious inputs, overload, and adversarial attacks. For our Cats vs Dogs classification model deployed as an API endpoint (see \texttt{src/serve.py}), we consider the following testing dimensions.

\textbf{Functional testing:}
\begin{itemize}
    \item Verify \texttt{POST /predict} returns correct JSON response with class label and confidence score.
    \item Test with valid cat and dog images to confirm correct classification.
    \item Test with proper error handling for missing or malformed request bodies.
\end{itemize}
This can be automated using \texttt{pytest} with the \texttt{requests} library, or via Postman/Newman for manual and CI/CD-integrated testing. Our implementation (\texttt{src/serve.py}) includes error handling for missing image fields and invalid file formats.

\textbf{Robustness testing:}
\begin{itemize}
    \item Submit non-image files (PDF, text) and verify graceful error responses.
    \item Submit corrupted image data and verify no server crash.
    \item Submit extremely large images to test memory limits.
    \item Submit images of objects that are neither cats nor dogs (out-of-distribution) to verify the model handles edge cases.
\end{itemize}

\textbf{Performance testing:}
\begin{itemize}
    \item Use Locust to simulate concurrent users and measure response times under load.
    \item Verify latency stays below acceptable thresholds (e.g., $<$200 ms for real-time classification).
    \item Identify the breaking point where throughput degrades.
\end{itemize}

\textbf{Security testing:}
\begin{itemize}
    \item Rate limiting to prevent abuse (e.g., max 100 requests/minute per client).
    \item Input validation to reject payloads exceeding maximum size.
    \item Authentication and API key management.
    \item OWASP ZAP for automated penetration testing (SQL injection, XSS).
\end{itemize}

\textbf{Safeguards against undesired input/output:}
For an image classification model, the primary safeguards are (1) input validation, rejecting non-image files, oversized images, and rate limiting, (2) confidence thresholds, returning ``unknown'' when the model's softmax probability is below a threshold (e.g., 70\%), which guards against out-of-distribution inputs, and (3) output sanitization, ensuring the API never exposes internal model details or stack traces.

In our specific case, the most important safeguards are confidence thresholds (to handle images that are neither cats nor dogs) and rate limiting (to prevent resource exhaustion on edge devices with limited compute).

\subsection{D6.3: Drift Detection and Mitigation}

Drift detection is important for the Cats vs Dogs pipeline. Silent model degradation can go unnoticed, so early detection enables timely retraining. The carbon cost of retraining is tracked in \Cref{tab:annual-carbon}.

\textbf{Types of drift} relevant to our Cats vs Dogs classifier:

\begin{itemize}
    \item \textbf{Data drift}: The distribution of input images changes (e.g., different camera types, lighting conditions, breeds, or image resolutions compared to the training set).
    \item \textbf{Concept drift}: The relationship between features and labels changes (less likely for cat/dog classification, but possible if the definition of ``categories'' shifts or new breeds emerge).
\end{itemize}

\textbf{Detection strategy:}

Our drift detection script (\texttt{src/drift\_detector.py}) checks for drift in two ways:

\begin{enumerate}
    \item \textbf{Feature-level drift} (data drift): The Kolmogorov-Smirnov (KS) two-sample test compares the distribution of each feature between a reference dataset and incoming production data. For each feature, the KS statistic and p-value are computed. If the p-value falls below a significance threshold (default: 0.05), drift is flagged for that feature. The script outputs per-feature drift results in a JSON report (\texttt{results/drift\_detection\_report.json}).

    \item \textbf{Performance-level drift} (concept drift): The script compares the model's current accuracy against a baseline accuracy. The accuracy drop is classified into severity levels as \textit{low} ($\leq$5\%), \textit{moderate} (5\% to 10\%), \textit{high} (10\% to 15\%), and \textit{critical} ($>$15\%). Based on severity, the script recommends either continued monitoring, close observation, or immediate retraining.
\end{enumerate}

\textbf{Mitigation strategy:}

When drift is detected, the following steps would be taken:
\begin{enumerate}
    \item \textbf{Alert}: Trigger a notification (e.g., via webhook or email) when drift metrics exceed a threshold.
    \item \textbf{Diagnose}: Inspect the drifted samples to understand the nature of the shift (new breeds, lighting changes, out-of-distribution images).
    \item \textbf{Retrain}: Trigger a retraining pipeline (via the Jenkins stages described in \Cref{sec:continuous-ml}) with updated data that includes representative samples from the shifted distribution.
    \item \textbf{Validate}: Compare the retrained model against the previous version on both old and new data distributions before promoting to production.
    \item \textbf{Deploy}: Use the MLflow Model Registry to promote the new model version to Production stage, which the serving API picks up automatically.
\end{enumerate}

\subsection{D6.4: Monitoring Metrics}

We bring together carbon footprint (\Cref{tab:carbon,tab:annual-carbon}), drift signals, and model performance into a single MLflow dashboard. \section{Guest Lecture}\label{sec:guest-lecture}

The final module consisted of three guest lectures on MLOps in practice, followed by short presentations where one member from each project group described their group's MLOps pipeline. This section is presented before Post Deployment (\Cref{sec:post-deployment}) to follow the order in which the modules were taught; the documentation IDs (D8.1 here, D7.1-D7.2 in Post Deployment) keep the course's own numbering. The goal of this module was not to introduce a new technique but to learn how other groups solved the same MLOps problems with different tools and design choices.

\subsection{D8.1: Key Takeaways from Guest Lectures and Presentations}

The three guest lectures covered AI and machine learning at Aalborg Portland, DevOps and MLOps in industry, and federated learning. No detailed notes or slides were kept from these talks, so we focus on the pipeline presentations, where the material was available.

Three groups presented their pipelines. Every group built a pipeline for image classification, but the tools and ideas each group highlighted were different, as shown in \Cref{tab:presentations}.

\begin{table}[h]
\centering
\caption{Key tools and ideas from the three pipeline presentations.}
\label{tab:presentations}
\begin{tabularx}{\linewidth}{@{} l X @{}}
\toprule
\textbf{Presentation} & \textbf{Notable idea} \\
\midrule
Vision Transformer on Oxford-IIIT Pet & 65\% accuracy gate before a model is registered \\
Data validation and AI-Lab & Container image cached by hashing the Dockerfile and requirements \\

\textbf{Vision Transformer group.} This group fine-tuned a Vision Transformer on the Oxford-IIIT Pet dataset across 37 breeds and reached 93.5\% accuracy. Their pipeline ran twelve Jenkins stages from checkout to deployment, and a model could only be registered if its accuracy passed a 65\% gate. An automated quality gate stops a degraded model from reaching production. Our pipeline uses the same approach, where model registration only happens when accuracy passes a fixed threshold (see \Cref{sec:continuous-ml}).

\textbf{Group 1.} This group used Great Expectations to validate the dataset before training, checking that files load, that labels are present, and that the input shape is correct. They also cached their Singularity containers by hashing the Dockerfile and the requirements file, so a new image is only built when one of these files changes. Since our training also runs in Singularity on AI-Lab, this caching approach saves build time.

\textbf{ONNX and FastAPI group.} This group separated training from serving by exporting the model to ONNX and serving it through FastAPI, so the production container does not depend on PyTorch. They used MLflow as an approval step where a person confirms a model before it is deployed. One useful point is that a pipeline is not better just because it is larger. Their serving setup with ONNX and FastAPI shows an inference API that our ResNet18 pipeline lacks. Exporting to ONNX for CPU inference could be a useful next step.

These presentations show that the same MLOps goals can be reached with different tools. The container caching and ONNX serving split are practical improvements we could add to our pipeline.

\section{Post Deployment}\label{sec:post-deployment}

This module covers techniques for managing deployed models over time, namely continual learning to handle new tasks without forgetting, and machine unlearning to remove what the model learned. Both exercises use the course's provided setup on MNIST digit classification instead of our Cats vs Dogs ResNet18 model from \Cref{sec:intro}. The techniques work on any dataset and architecture, so we can apply them directly to the deployed classifier, for example to adapt to new breeds without forgetting existing classes or to remove specific training data on request.

\subsection{D7.1: Na\"ive Continual Learning vs. Replay + EWC}

Catastrophic forgetting occurs when a neural network trained on new data loses its ability to perform on previously learned tasks. We demonstrate this effect and then reduce it by using experience replay and Elastic Weight Consolidation (EWC).

\textbf{Setup:} A simple MLP (784$\to$256$\to$128$\to$10) was trained sequentially on two tasks:
\begin{itemize}
    \item \textbf{Task 1}: Digits 0-4 (5 epochs)
    \item \textbf{Task 2}: Digits 5-9 (5 epochs)
\end{itemize}

\textbf{Na\"ive sequential training} (no replay): After training on Task 2, accuracy on digits 0-4 dropped from 98.4\% to 0.3\%, which is almost complete catastrophic forgetting. The model could only classify the new digits, reaching 98.6\% on 5-9 and 48.1\% total accuracy.

\textbf{Experience Replay + EWC}: A memory buffer of 500 samples from Task 1 was stored. During Task 2 training, these were replayed alongside new data. Additionally, EWC applied a regularization penalty ($\lambda=400$) that protects weights important for Task 1, estimated via the diagonal Fisher Information Matrix.

\begin{table}[h]
\centering
\caption{Continual learning results on MNIST (accuracy \%).}
\label{tab:continual}
\begin{tabular}{@{} l r r r @{}}
\toprule
\textbf{Method} & \textbf{Digits 0-4} & \textbf{Digits 5-9} & \textbf{Total} \\
\midrule
After Task 1 only & 98.4 & -- & -- \\
Na\"ive sequential & 0.3 & 98.6 & 48.1 \\
Replay + EWC & 85.9 & 98.6 & 92.1 \\
\bottomrule
\end{tabular}
\end{table}

Replay + EWC recovers 85.9\% accuracy on old digits while maintaining 98.6\% on new digits, showing that a small memory buffer and weight regularization together effectively stop catastrophic forgetting. The drop from 98.4\% to 85.9\% on old digits shows the stability-plasticity tradeoff, where learning new tasks with only a small replay buffer makes some forgetting of old tasks unavoidable.

\Cref{fig:continual} shows the catastrophic forgetting effect and how replay with EWC recovers on MNIST. The figure shows the three configurations. Task 1 reaches 98.4\%, naive sequential training drops to 0.3\% on the old digits, and replay with EWC recovers to 85.9\%.

    \caption{Continual learning on MNIST. Na\"ive sequential training forgets the old digits almost completely (0.3\% on 0-4), while replay combined with EWC keeps 85.9\% on the old digits and 98.6\% on the new digits.}
    \label{fig:continual}
\end{figure}

\subsection{D7.2: Machine Unlearning with Gradient Ascent}

Machine unlearning aims to selectively remove the influence of specific training data from a model without retraining from scratch. This is relevant for GDPR compliance (``right to be forgotten'') and removing biased or copyrighted content.

\textbf{Setup:} A classifier was trained on full MNIST (0-9) achieving 97.5\% baseline accuracy. The goal was to make the model forget digit ``7'' while retaining performance on the remaining digits.

\textbf{Method:} Gradient ascent unlearning maximizes the loss on the forget class, effectively pushing the model away from correctly classifying that digit. The update rule is as follows.

\begin{verbatim}
loss = -criterion(model(x), y)  # maximize loss
loss.backward()
optimizer.step()
\end{verbatim}

\Cref{tab:unlearning} shows the per-class accuracy results after 3 epochs of gradient ascent ($\text{lr}=5 \times 10^{-5}$) on digit 7 samples, followed by 2 epochs of fine-tuning on the remaining classes to stabilize.

\begin{table}[h]
\centering
\caption{Unlearning results: per-class accuracy (\%) before and after forgetting digit 7.}
\label{tab:unlearning}
\begin{tabular}{@{} c r r r @{}}
\toprule
\textbf{Digit} & \textbf{Before} & \textbf{After} & \textbf{Diff} \\
\midrule
0 & 98.4 & 98.9 & $+$0.5 \\
1 & 99.4 & 99.1 & $-$0.3 \\
2 & 97.9 & 97.6 & $-$0.3 \\
3 & 96.7 & 97.4 & $+$0.7 \\
4 & 98.3 & 98.2 & $-$0.1 \\
5 & 96.9 & 98.0 & $+$1.1 \\
6 & 98.4 & 97.7 & $-$0.7 \\
\textbf{7} & \textbf{96.9} & \textbf{0.0} & $-$\textbf{96.9} \\
8 & 97.9 & 97.3 & $-$0.6 \\
9 & 97.9 & 96.3 & $-$1.6 \\
\bottomrule
\end{tabular}
\end{table}

\begin{figure}[h]
    \centering
    \includegraphics[width=\linewidth]{figures/unlearning.png}
    \caption{Per-class accuracy before and after unlearning digit 7. Digit 7 drops to 0.0\% while the other nine classes average 97.8\%.}
    \label{fig:unlearning}
\end{figure}

Digit 7 was successfully unlearned (0.0\% accuracy) while the remaining classes maintained an average accuracy of 97.8\%, nearly identical to the baseline. To get this result, we balanced the unlearning strength (3 epochs with a small learning rate) with a short fine-tuning phase on the retain data to keep shared knowledge steady. Without fine-tuning, gradient ascent hurts other classes because the model's knowledge is spread across many parameters. Fine-tuning on the other classes restores them. To make gradient ascent work, we need to tune the unlearning strength carefully. If it is too strong we break other digits, and if it is too weak digit 7 is not fully forgotten.

\textbf{1. Continual learning} (\texttt{src/continual\_learning.py}): Three-stage experiment on MNIST showing catastrophic forgetting and how replay reduces it via experience replay (500-sample buffer) combined with EWC regularization ($\lambda=400$, diagonal Fisher Information Matrix).

\textbf{2. Machine unlearning} (\texttt{src/unlearning.py}): Gradient ascent unlearning of digit 7 followed by retain fine-tuning. Demonstrates successful targeted forgetting with documented side effects to remaining classes.
